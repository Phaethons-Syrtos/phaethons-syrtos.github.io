向量数据库这两年有点被说烂了。但大多数讨论停在「用 HNSW 还是 IVF」「召回率多少」，很少有人认真谈落盘之后的事：索引怎么摆在页上、更新怎么不把图拆坏、带标量过滤的查询怎么不退化成全表扫。这篇论文正好补的是这一段。

《GaussDB-Vector: A Large-Scale Persistent Real-Time Vector Database for LLM Applications》，PVLDB 18(12)，清华的 Ji Sun、Guoliang Li、James Pan 和华为的几位。核心主张很直接：向量库不该在「内存里快」和「数据库该有的数据管理能力」之间二选一。

## 它要解决的四个具体毛病

论文先摆了三类现有系统的问题，我觉得总结得挺克制：

- **Milvus** 把数据组织成 LSM 的 segment，每个 segment 建一份索引。查询要把所有 segment 都搜一遍再归并；合并、分裂 segment 要重建索引，更新很贵；只支持 pre-filtering，也就是先按标量筛再算向量；新写入的数据不立刻进索引，新鲜度差。
- **ElasticSearch** 本来是做文本检索的，向量是后加的能力，段结构带来同样的问题。
- **PGVector** 在 PostgreSQL 的页上建 HNSW。单机、按页访问，磁盘上随机 I/O 比 NSG、DiskANN 这类为磁盘设计的图更重，也没法扩到十亿级。

这四条其实指向同一个矛盾：**向量检索的性能来自「连续、可预取」，而数据库的更新要求「随机、就地」**。谁能在两者之间找到稳定的折中，谁就能既快又不丢数据。

## 整体架构：先承认它是个数据库

GaussDB-Vector 用的是 CN/DN 两层结构：协调节点负责接连接、解 SQL、做执行计划，数据节点负责算子执行和存储管理，另有集群管理器和全局事务管理器。这套东西不新，但用它做向量库有个直接好处——SQL 优化器可以在顺序扫描和索引扫描之间选，带过滤条件的复杂查询能走代价模型，而不是靠应用层拼。

接口上也确实像数据库：`floatvector(128)` 是个列类型，距离用运算符表达，`<cos>`、`<euc>`、`<ham>` 分别对应余弦、欧氏、汉明。建索引用 `CREATE INDEX ... USING {IVF|VAMANA}`，还支持 `CONCURRENTLY`——先按快照建，再吃增量，避免几个小时的建索引把业务堵死。

## 索引：页式布局 + 两种 ANN 结构

存储是页式的，向量和其他列一起按行存，索引则是一个独立的结构化文件：元数据页、簇页、数据页。为了减少随机页访问，相近的向量会被放到物理连续的数据块里。

**IVF 这条线**做得比较细。它用两层聚类来均衡簇的负载；默认把第一层和第二层分别取各自簇数的 10% 再开方，让候选集覆盖 5%–10% 的数据。top-k 的取数没有整表排序，而是按距离做二分式的收缩（论文叫 binary sort），复杂度压到 `O(|Vc|)`，再逐行检查可见性——这样异步删除和多属性过滤留下的「无效行」不会把查询拖死。删除是先打标记，物理清理由后台批量做；vacuum 在删除量超过 10% 时触发，按簇加共享锁复制存活向量，只短暂阻塞单个簇的写入。

**图这条线**基于 Vamana（DiskANN 那一支）。论文里最有意思的是它按维度分了三种页布局：

| 维度区间 | 布局 | 省的是什么 |
| --- | --- | --- |
| 小于 130 | 向量、PQ 码、邻居码塞在同一页 | 一次 I/O 拿到当前点和全部邻居的码 |
| 130 到 1565 | 邻居只存 tuple ID，PQ 码挪到单独区域 | 避免单页放不下，PQ 总量小、可常驻内存 |
| 大于 1565 或十亿级 | 节点与边彻底分开，开了 PQ 还能丢掉原始向量 | 存储和缓存压力 |

这两个阈值不是拍的：按 96 个邻居、6 字节 tuple ID、4 字节浮点、最多 96 字节 PQ 码、每页 8 KB 反推出来的。工程论文里这种「数字有出处」的细节，比结论更值得看。

它还做了一层很克制的缓存：**只**缓存搜索时前两步访问过的节点和边，加上 PQ 表和 PQ 码，论文管这些点叫热节点，其余的全交给操作系统的页缓存。规则这么窄，是为了让缓存本身不至于变成新的负担。

建图也不是一把梭。它先把向量聚成 N 个**互相重叠**的簇，每个向量属于最近的两个簇，然后在每个簇里建出度只有一半（48）的子图，最后合并成出度 96 的全局图。这样建图能在内存里完成、不用频繁换出，全局连通性又靠「每个点属于两张子图」保住。重复向量会被并成一个节点、只让主节点参与选邻居——否则重复点容易抱团成团块，搜索掉进局部最优，召回直接塌。

插入时的剪枝是我最想记的一处。DiskANN 给新点连反向边时，要对每个邻居检查它所有的邻居，最坏 `O(m³)`；这里改成对邻居的邻接表做线性扫描、用「最远的那个邻居」当支配性判定的启发式，把复杂度降到 `O(m²)`。配上 1.2 的松弛系数——论文引用 Filtered-DiskANN 的结论，说这个系数能让图在 40% 数据被删之后仍然稳定——插入路径短了，图的质量也没还回去。

删除另有个坑：图里不保证能用 ANN 找到要删的那个点。它的解法是加一张倒排表，用堆表里的 ctid 反查索引内的 tid，绕开这个不确定性，顺带支持「先删后插」的就地更新，减少垃圾堆积。

## 混合查询：把向量子索引挂到 B+ 树上

标量加向量的过滤查询，常见做法是扩大候选集硬扫，选择率一低就退化成灾难。这篇的做法是把两套结构缝在一起：标量走 B+ 树，**每个根节点和中间节点都挂一个向量子索引**。

于是查询可以按选择率分流：谓词命中超过 50% 的数据时，直接在那个节点的向量子索引里找答案，不用扫全部叶子；命中很少时，定位到叶子、对少量向量排序就够了。叶子节点不建子索引——叶子一般不到 100 个 tuple，顺序扫更快，而且叶子分裂最频繁，挂索引的维护成本划不来。

这里能看出一个很清醒的取舍：**搜索性能和更新效率是互斥的**。节点越多、挂的子索引越多，查得快、改得慢。所以它只在根和中间节点建索引，而且图子索引只给超过一千万向量的节点用——建图的代价得能被查询收益抵回来。

## 分布式：按距离分片，按基数路由

分片不是哈希，是**按距离**：把向量分成 c 簇，每簇对应一个数据节点，簇心放在协调节点。整个过程有四个状态：数据量小的时候随机撒（RANDOM），到五万条左右开始全量重分布（FULL REDISTRIBUTING，短暂阻塞更新、查询发给所有节点），簇心定下来之后新向量进最近的节点、老的慢慢搬（CLUSTERED），之后定期采样、重标号，漂移超过 10% 再增量重分布。

路由这块借的是作者自己 SIGMOD'21 的基数估计工作：每个数据节点在 `ANALYZE` 时用采样训一个基数模型，存在协调节点。范围查询拿距离阈值直接估各节点的基数；top-k 则对距离做二分，找到「各节点估计基数之和刚好超过 k」的那个阈值，只发给贡献大的节点。混合查询把标量选择率一并算进去。

基数估计必然有误差，论文还补了一刀：靠近簇心的查询向量最稳，靠近簇边界的掉得最狠。所以除了按估计值选簇，它还会额外选那些「簇心到查询向量的距离不超过已选簇最大距离」的簇——一个便宜的兜底。

高可用这块论文没展开，只交代了机制：为向量的插入、删除、更新新增了对应的日志类型，副本之间按日志重放；堆表和索引都存副本；主节点失效时重新选举。这些对数据库是基本盘，对向量库却是不少产品的空白。

## 硬件加速：矩阵化，但不是万能

距离计算被写成 `D(x, y) = x² − 2xyᵀ + y²`，转成矩阵乘，交给 Ascend NPU 或 GPU 批处理；`x²` 可以在向量入索引时预先算好。构造索引时，IVF 的聚类和打标、图索引剪枝时的距离计算都能搬到 NPU 上，论文报告建索引有 1 到 2 个数量级的提升。

但它也老实说了：**图搜索的提升不明显**，因为图遍历本身难并行，跨设备搬数据的开销把并行收益吃掉了。这种「哪块加速有效、哪块没有」的交代，比通篇吹硬件诚实。

## 实验说了什么

测试集是 SIFT（1000 万，128 维）、GIST（100 万，960 维）、HUAWEINet（1500 万，1024 维），各自加了一列标量做混合查询，另外把 SIFT 扩到 100 亿。基线是单机的 ElasticSearch、Milvus、PGVector，统一用它们支持的最好索引 HNSW。

结论大概是：

- 单机十亿级，延迟 50 ms 以内、召回 95% 以上；多机可以到百亿级、十万级 QPS。
- 单连接、多连接、QPS、插入延迟四条曲线里都领先，整体 1 到 5 倍。
- 混合查询比基线好 70% 到 300%，而且选择率从 90% 变到 10% 时曲线基本不塌——这是那个「B+ 树挂子索引」设计最直接的回报。
- 百亿数据、40 台机器：99% 召回、约 60 ms、1500 QPS；30 台以内扩容接近线性，再多就被数据搬运和结果归并拖住。
- 更新吞吐会周期性下滑，vacuum 之后恢复，最大回退 5% 到 15%。
- 真实用例是华为内部的编码助手：十亿级 tuple，搜索峰值 5000 QPS、更新 3000 QPS，平均 100 ms 内完成。

## 我觉得值得记的三点

第一，**它把「实时」当成硬指标而不是优化项**。新写入提交即可见、支持 ACID、删除走惰性加后台清理、vacuum 分簇短锁——这一整套是数据库的做法，不是向量检索库的做法。多数向量库在这块是含糊的。

第二，**它的性能来自布局，不来自更聪明的算法**。页怎么切、码放哪、边存不存 ID、子索引挂哪一层，全是 I/O 层面的算计。这也解释了为什么它敢说自己「持久化还能低延迟」：在 SSD 上，随机 I/O 的次数比距离计算更贵。

第三，**取舍写得比结论清楚**。图子索引只给大节点、叶子不建索引、NPU 只对建索引有效，这些都是「我不做什么」的声明，比堆指标有信息量。

不足也有：基线全是单机版，没和 SPANN、DiskANN、Filtered-DiskANN 这些同代工作直接对比；百亿规模只在 40 台机器上验证过；混合索引在节点分裂时要重建子索引，这部分代价论文只给了定性描述；另外开头提华为内部编码助手「万亿级代码生成查询」，那是查询量不是数据量，跟实验里的百亿向量不是一回事，读的时候别混。

## 最后

如果只记一句：**向量库的难点不在 ANN 算法，而在把 ANN 算法塞进一个有事务、有页、有锁、有副本的数据库里，还不让它变慢。** 这篇论文的价值，是把这句话拆成了一堆可以照着做的工程决定。
